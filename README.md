# Network + DPI Pilot

Один значок и один попап в баре: стоковая панель сети Omarchy (состояние соединения, скорость, Wi‑Fi, выбор DNS, проверка связности) плюс выдвижной ящик DPI Pilot для обхода DPI через [zapret2](https://github.com/bol-van/zapret2). Отдельный значок `omarchy.network` больше не нужен — все сетевые функции собраны здесь.

Плагин сам **генерирует стратегии**: собирает конфигурации `nfqws2` из примитивов (fake, multisplit, multidisorder, TTL, seq, QUIC), применяет их по очереди, проверяет YouTube, Discord и Google и оставляет ту, что реально работает быстрее. Готовые пресеты не используются.

Это отдельное решение, не форк и не надстройка над `omarchy-zapret2`. Кроме DPI-обхода есть необязательный **WARP** — свой генератор конфига для mihomo (MASQUE, без `wgcf` и без клиента Cloudflare).

Код переписан с нуля: вместо одного большого `kich-dpi` — пакет `src/kich_dpi/` из тонких фасадов и небольших модулей по обязанностям (установка, шаблоны, статус, подбор, WARP, восстановление). Публичные имена в `cli.py`, `core.py`, `engine.py`, `status.py`, `strategies.py`, `warp.py` и `repair.py` сохранены: это точки вызова и patch-точки тестов. QML-часть — стоковая сетевая панель (`DpiPilot.qml` + `NetworkModel.js`) со встроенным `DpiSection.qml`; чистые функции форматирования вынесены в `DpiModel.js`.

## Что в интерфейсе

Клик по значку открывает знакомый попап сети: герой-блок с состоянием и действиями, детали соединения, выбор полосы Wi-Fi, список сетей и DNS-провайдер. Внизу через разделитель идёт disclosure-блок DPI Pilot: его шапка видна всегда, подробности скрыты до нажатия на неё. Кнопки и шапка используют штатные компоненты Omarchy: прямые углы из темы, контур как у DNS-пилюль, подсветку при наведении, цвет нажатия, лёгкое уменьшение при клике, фокус-рамку и системные подсказки. Щит DPI Pilot выровнен по левому краю с иконкой сети в стоковой шапке выше и повторяет её размер и расстояние до текста.

В шапке DPI — иконка-щит DPI Pilot, статус и одна строка диагностики вида `DPI 3/3 · WARP ok · Система 12/12`. Справа две компактные иконки: **сердечко восстановления** и **обновить**. Сердечко краснеет вместе с тумблером неработающего DPI и/или WARP. Клик по остальной части шапки раскрывает:

- **Обход DPI** и **WARP** — карточки с настоящими тумблерами. Если движок ещё не установлен, вместо них показывается кнопка установки. Переключение не требует polkit; состояние хранится в `~/.config/kich-dpi/state.json`, systemd-юниты остаются включёнными, а при выключенном тумблере ничего не запускают.
- **ДОСТУПНОСТЬ** — три точки YouTube/Discord/Google и время последней проверки. Показывается только при включённом DPI, чтобы старые результаты не красили выключенный сервис в красный.
- **Подобрать / Проверить** — единственная кнопка диагностики запускает `check-all`; подбор показывает прогресс `N/18`. Список стратегий больше не занимает попап: он спрятан в **Дополнительно** вместе с обновлением движка, перерегистрацией WARP и удалением с подтверждением.
- **Восстановить** — одна кнопка для известных поломок: добавит недостающие домены Discord (`discord.gg`, `discordapp.net`) в `dpi-domains.txt`, закрепит медиа-домены Discord на рабочие IP в `/etc/hosts`, если их anycast-диапазон недоступен, перезапустит DPI и WARP. Polkit запрашивается только потому, что правится `/etc/hosts`. Повторное нажатие ничего не меняет.

Набор проверок берётся из желаемого состояния: включён DPI — проверяются YouTube, Discord и Google; включён WARP — туннель через локальный прокси mihomo с флагом `tun`; системная диагностика работает всегда. Выключенный тумблером сервис не проверяется и в строку не попадает. Отдельные команды `check`, `warp-check` и `doctor` остались доступны в CLI и IPC.

Команда `check-all` для кнопки собрана в `src/kich_dpi/doctor.py` (фасад — `status.py`): она вызывает уже существующие `strategies.run_check()` и `warp.warp_check_data()` (их кэш затем читает `snapshot.py`), а системные строки берёт из `doctor_checks()` — с поправкой на то, что намеренно выключенная служба не считается поломкой.

DPI-ящик опрашивает `status` только пока попап открыт (каждые 2.5 с; 1.2 с во время подбора). Закрытое окно не держит таймеры и не порождает процессы. `Esc` закрывает попап. IPC-команды `service`, `warp`, `check`, `doctor`, `warpCheck`, `generate`, `repair`, `refresh` работают даже до первого открытия: запрос ставится в очередь и выполняется после первого ответа `status`. `check` запускает ту же объединённую проверку, что и кнопка; `doctor` и `warpCheck` — отдельные проверки.

Иконка в баре и элементы управления белые, пока включённые сервисы проходят проверки. Красный цвет появляется только при реальной поломке: DPI запущен, но сайты не открываются, либо WARP запущен, но не достукивается до выхода. Если тумблер намеренно выключен, это не считается поломкой.

## Установка

Из локального каталога:

```bash
ln -s ~/Work/omarchy-dpi-pilot ~/.config/omarchy/plugins/kich.dpi-pilot
omarchy restart shell
omarchy bar put kich.dpi-pilot
```

Или как обычный плагин:

```bash
omarchy plugin add https://github.com/kichcloud/omarchy-dpi-pilot.git --enable --yes
```

Если раньше в баре был этот плагин вместе со стоковым `omarchy.network`, уберите лишний значок: удалите `{ "id": "omarchy.network" }` из `bar.layout.right` в `~/.config/omarchy/shell.json` (или через настройки бара). `shell.json` подхватывается без перезапуска шелла.

Дальше откройте попап DPI Pilot и нажмите **«Установить движок»**. Установка скачивает официальный релиз `bol-van/zapret2`, сверяет `sha256` из GitHub и один раз спрашивает пароль через `pkexec`. Движок и системный юнит живут отдельно от других плагинов:

| Путь | Что |
| --- | --- |
| `/opt/kich-dpi/` | `nfqws2`, Lua-библиотеки, фейки, `mihomo` и копия менеджера |
| `/etc/systemd/system/kich-dpi.service` | служба обхода |
| `/etc/systemd/system/kich-dpi-warp.service` | служба WARP (mihomo) |
| `/etc/polkit-1/rules.d/49-kich-dpi.rules` | start/stop/restart двух юнитов без пароля; `manage-unit-files` не нужен |
| `/etc/sysctl.d/90-kich-dpi.conf` | `nf_conntrack_tcp_be_liberal=1` |
| `~/.local/state/kich-dpi/` | **единственный** каталог конфига и состояния: `state.json`, `active.json`, `strategies.json`, `warp.yaml`, списки доменов, `rules/`, `account.json` (0600), `nfqws2.conf`, результаты проверок и прогресс подбора |
| `~/.config/kich-dpi` | симлинк на каталог выше — старые пути и `ConditionPathExists` в юните продолжают работать, `/etc` не меняется |

С 0.4.0 всё изменяемое состояние лежит в `~/.local/state/kich-dpi`; каталоги `~/.local/share/kich-dpi` и `/run/kich-dpi` больше не создаются, а аккаунт WARP из старой раскладки переносится автоматически. Начиная с этой версии туда же переезжают и файлы конфига: `setup` один раз переносит их из `~/.config/kich-dpi` и оставляет вместо старого каталога симлинк. Код работает с путями в state-каталоге; `~/.config/kich-dpi` остаётся только совместимым симлинком, поэтому `ConditionPathExists` юнита видит `warp.yaml`, а root-created каталог не мешает пользователю создавать файлы.

## Как работает подбор

`./kich-dpi generate` строит 18 конфигураций из комбинаций:

Подбор всегда идёт по физическому интерфейсу в обход WARP: иначе проверка видит только туннель и выбирает стратегию, которая ломает прямой TLS. Каждая конфигурация дополнительно проверяется на `ya.ru`, `example.com`, `aur.archlinux.org`, `www.gosuslugi.ru`, `api.proxyapi.ru`, `console.proxyapi.ru` и `opencode.ai`; если прямой TLS к ним не работает, вариант отбрасывается.

AUR в этом списке — самая строгая проверка, и появился он не сразу. Он стоит за anycast-HAProxy, которая на ClientHello с опцией маскировки `tcp_md5` отвечает алертом `tlsv1 unrecognized name`. То есть ломались все варианты, кроме двух с `tcp_seq` и `tcp_flags`, а `generate` этого не замечал: YouTube открывался, а `pacman` и `yay` молча теряли индекс AUR. Ошибка вылезла только когда пользователь сообщил, что AUR не работает при выключенном WARP.

Госуслуги добавились по той же причине: стратегии семейства fake+split без отказа открывали YouTube, Discord и AUR, но систематически обрывали TLS к `www.gosuslugi.ru` (3/3 таймаута по 7 с при доступности 200 за 0.1 с без обхода). Оба proxyapi-адреса проверяются потому, что предыдущие конфигурации уже рвали соединение с `api.proxyapi.ru`, и «успешная» стратегия не должна лишать доступа к сервису, которым пользуется машина.

Конкретный победитель зависит от сети и от того, включён ли селективный режим: после перехода на список доменов в текущей сети им стал `fakedsplit at 1`. Это не «лучший пресет на все случаи» — результат нужно смотреть по выводу `generate` в своей сети. Разница между вариантами в том, какую позицию и какой тип рассечения они используют: одни лучше держат Discord, другие — Госуслуги, поэтому взвешенная оценка и проверка сторонних сайтов здесь важнее конкретного названия.


- fake + multisplit / multidisorder;
- fakedsplit / fakeddisorder;
- позиции `1`, `2`, `midsld`, `1,midsld`, `sld+1`;
- фулинг `tcp_md5`, `ip_ttl`, `tcp_seq`, `tcp_flags_unset=ack`;
- fake для TLS и QUIC, разное число повторов.

Для каждой стратегии служба перезапускается, затем три запроса `curl` измеряют код ответа и время. Взвешенная оценка приоритизирует `discord`, `youtube`, `api.proxyapi.ru`, `opencode.ai` и `console.proxyapi.ru`; `google` считается малозначимым. Стратегия, потерявшая приоритетный сервис, не может победить только потому, что у неё ниже задержка. В конце применяется лучшая стратегия; если текущее состояние по взвешенной оценке не хуже, остаётся текущая. Всё это видно в попапе как «N / 18» и название текущей конфигурации.

По умолчанию десинхронизация применяется **только к нужным сервисам**, а не ко всему трафику: в конфиг nfqws2 добавляется `--hostlist-domains` с доменами из `~/.config/kich-dpi/dpi-domains.txt` (поддомены учитываются автоматически). Начальный список: Discord, YouTube, `googlevideo.com`, `ytimg.com`, `ggpht.com`, `discord.media`. Файл создаётся сам; чтобы вернуть старое глобальное поведение, оставьте его пустым (только комментарии) — тогда `--hostlist-domains` не добавляется и обход снова работает на всех TCP 80/443 и UDP 443.

Голос Discord отдельно: IP-discovery и STUN идут по UDP `19294-19344` и `50000-50100`, у этих пакетов нет домена, поэтому общий `--hostlist-domains` к ним не применяется. Для них в nftables есть отдельная очередь, а в nfqws2 — два профиля с `--filter-l7=discord` и `--filter-l7=stun`, подменяющие DPI QUIC-фейками. Рукопожатие голоса может уйти на нестандартные TCP-порты `2053,2083,2087,2096,8443`: они тоже очередируются, и для `discord.media` на них применяется `multisplit` с seqovl. Обычный RTP-трафик после установки соединения не трогается.

Пакеты внутри TUN (если рядом работает WARP) пропускаются правилом `meta oiftype 65534 return`, а адреса MASQUE-шлюзов Cloudflare исключены из очереди отдельно — иначе обход ломал бы рукопожатие самого туннеля.

Пакеты, которые nfqws2 обработал, помечаются меткой `0x10000000`, и правило `ip rule fwmark 0x10000000/0x10000000 lookup main priority 8999` возвращает их в основную таблицу маршрутов. Без него при поднятом WARP mihomo затягивал в туннель и их (правило `iif lo → table 2022`), стек gvisor не мог воспроизвести такие пакеты, и рукопожатие висело до таймаута.

Из-за этого же эффекта раньше приходилось пропускать из очереди метку `0x20000000`, которую mihomo ставит своим сокетам, — и DPI не трогал прямой трафик mihomo вовсе. Правило маршрутизации убрало причину, пропуск сняли. Замер: Discord, принудительно отправленный напрямую, без пропуска открылся `200` за 0.3 с, с пропуском висел 15 с до таймаута; Госуслуги (5/5), mos.ru, nalog.gov.ru, vk.com, ya.ru отвечают одинаково в обоих режимах. Теперь российские сайты, которые mihomo отправляет DIRECT, обходятся и при включённом WARP. `routing-mark` в конфиге оставлен просто как метка сокетов mihomo — на маршрутизацию она не влияет.

Это же правило чинит проверку связи NetworkManager: её запрос привязан к физическому интерфейсу (`CURLOPT_INTERFACE`, `if!enp8s0`), и без правила оболочка писала «ограниченный доступ в интернет» на полностью рабочем канале.

## WARP (необязательно)

WARP здесь — не `wgcf` и не `warp-cli`, а свой генератор:

1. при первом включении менеджер создаёт ключ P-256 через `openssl` и регистрирует устройство напрямую в Cloudflare API с `tunnel_type=masque`;
2. собирает `~/.config/kich-dpi/warp.yaml` для mihomo: TUN `kichwarp`, MASQUE поверх QUIC, fake-IP DNS — не по шаблону «для всех», а под текущую машину;
3. запускает `kich-dpi-warp.service` от вашего пользователя с `CAP_NET_ADMIN`.

Перед сборкой конфига плагин считывает реальную сеть: интерфейс и шлюз маршрута по умолчанию, подсеть из `ip route` (вместо жёстких `192.168/16`, `10/8`, `172.16/12`), MTU интерфейса, текущие DNS из `resolvectl`, наличие глобального IPv6. В конфиг попадают ваша подсеть, ваши DNS и `ip-version: ipv4-only`, если IPv6-маршрута нет. Шлюз выбирается не по TCP-порту, а настоящим рукопожатием MASQUE через mihomo: закреплённый адрес остаётся, если он работает; sibling получает конфиг, только если трафик реально пошёл через WARP. Пересобрать конфиг вручную можно `./kich-dpi warp-config`.

Почему MASQUE, а не WireGuard: в российских сетях классический WG-WARP узнаётся и режется DPI, а MASQUE идёт по UDP 443. Почему mihomo, а не клиент Cloudflare: нужен конфиг с исключениями. Российские домены (Яндекс, VK, Госуслуги, банки, Ozon, Avito и другие), локальная сеть и частные подсети идут напрямую, остальное — через туннель. QUIC (UDP 443) тоже идёт через туннель: браузер пробует его первым, и напрямую он висит около десяти секунд, из-за чего страница выглядит мёртвой. Остальной UDP — звонки, игры, локальная сеть — остаётся напрямую. `warp-cli` так не умеет: consumer-клиент гонит в туннель весь трафик.

Отдельная проблема — видео YouTube: его медиа с `*.googlevideo.com` не отвечают с выходных адресов Cloudflare (страница открывается, а поток висит до таймаута). Поэтому YouTube, `googlevideo.com`, `ytimg.com`, `ggpht.com`, `gstatic.com` и `googleapis.com` добавлены в `direct-domains.txt`: страница и API идут через WARP, а само видео — напрямую. Если какой-то другой сайт стал медленнее именно через туннель, добавьте его домен туда же и сделайте `warp-on`.

Для сравнения ставился официальный `warp-cli`: его значения по умолчанию — MASQUE с гонкой HTTP/3 и HTTP/2, split-tunnel в режиме исключений и DNS через `cloudflare-dns.com`. На этой сети он выбирает шлюз `162.159.198.2` и не может поднять туннель (`happy eyeballs failed`), даже если явно указать рабочий `162.159.199.2`. Пока официальный клиент установлен, он должен оставаться `disconnect`: его фаервол мешает mihomo отправлять UDP-пакеты MASQUE.

### Списки правил

Исключения вынесены из кода в текстовые списки. Вместе с плагином едут два готовых, они же копируются в `~/.local/state/kich-dpi/rules/` при каждом `warp-on`. Каталог неслучаен: mihomo принимает пути `rule-providers` только внутри своего `-d`-каталога (у службы это `~/.local/state/kich-dpi`) и иначе отказывается стартовать:

- `ru-domain.txt` — 46 российских доменов (Яндекс, VK, Госуслуги, банки, маркетплейсы, операторы);
- `ru-ip.txt` — 8664 IPv4-префикса из данных пяти RIR (CC0, `ipverse/country-ip-blocks`).

При копировании в `~/.local/state/kich-dpi/rules/` к каждой строке домена добавляется `+.`. В mihomo список с `behavior: domain` без префикса совпадает только с точным именем: `yandex.net` не покрывал `api.music.yandex.net`, и музыка уходила в `MATCH,WARP`. `+.yandex.net` — это суффикс, как `DOMAIN-SUFFIX`, поэтому поддомены тоже остаются напрямую. Ваши файлы остаются простыми: `+.` добавляется только в сгенерированную копию.

У правила `RULE-SET,ru-ip,DIRECT` намеренно нет `no-resolve`. С ним mihomo не проверяет IP для доменных соединений (у них внутри TUN fake-IP, а адрес известен только по имени), и российский адрес, которого нет в списке доменов, уходил в туннель. Так `api.proxyapi.ru` (`139.100.192.0/18`) шёл через WARP, где вызов не открывался, и opencode падал с `ECONNRESET`. Без `no-resolve` префиксы `ru-ip` работают и для доменов; лишний резолв берётся из кэша mihomo.

Своё добавляйте рядом с конфигом, эти два файла не трогайте — при обновлении они заменяются:

```bash
# ~/.config/kich-dpi/direct-domains.txt — по одному домену в строке
my-internal.example
# ~/.config/kich-dpi/direct-processes.txt — по одному имени процесса (`ps -o comm=`)
telegram
```

Домены из `direct-domains.txt` попадают в правило `RULE-SET,direct-domains,DIRECT` (тоже через сгенерированную копию с `+.`), процессы — в `PROCESS-NAME,…,DIRECT` (они проверяются раньше всего остального). Пока `direct-processes.txt` пуст, в конфиге стоит `find-process-mode: "off"`: определять владельца каждого соединения незачем. Появилась хотя бы одна строка — включается `"strict"`. Списки применяются при следующем `warp-on`; из попапа хватит выключить и включить туннель.

### Проверка и защита от битого конфига

`warp-check` больше не спрашивает таблицу маршрутов, а идёт в туннель через локальный прокси mihomo (`mixed-port: 17890` на `127.0.0.1`). Так проверяется сам туннель, а не то, куда сейчас случайно ведёт маршрут по умолчанию. Отдельно проверка смотрит устройство маршрута по умолчанию: если это не `kichwarp`, в попапе рядом с адресом выхода появится «маршрут не в туннеле» — раньше такой случай выглядел как успех.

Служба WARP перед запуском прогоняет конфиг через `mihomo -t` (`ExecStartPre`). Без этого mihomo либо поднимался со старым файлом, либо падал молча, и трафик уходил мимо туннеля. Теперь битый конфиг виден как неудачный старт службы.


Шлюз по умолчанию закреплён — сейчас `162.159.199.2`. Пул из четырёх адресов с выбором по задержке оказался хуже: `197.2` и `196.2` часто отвечают `alive: false`, а `.1`-двойники отдают другой ключ и падают на `x509: remote endpoint has a different public key`. Поэтому sibling не выбирается по «открытому TCP-порту»: `warp-config` проверяет кандидата коротким рукопожатием MASQUE с вашим ключом и переключается, только если проверка прошла. Если ни один адрес не прошёл, остаётся закреплённый. Если туннель начнёт «зависать» с задержкой в пару секунд на рукопожатие, первым делом стоит сравнить шлюзы заново.

YouTube в России режется по IPv4, а WARP выходит из Москвы (`colo=DME`) — то есть в том же проблемном месте, и обычный туннель проблему не решает. Когда у машины есть IPv6-маршрут и глобальный адрес, прокси просит IPv6 у DNS (`ip-version: ipv6-prefer`): YouTube уходит по IPv6 внутри туннеля. Замер: 7 из 15 запросов по IPv4 против 15 из 15 по IPv6; в реальном TUN с DPI — 29 из 30. Домены без AAAA автоматически идут по IPv4. На сети без IPv6 конфиг принудительно использует `ipv4-only` и не пишет `inet6-address` в TUN: раньше это давало рукопожатие в никуда.

Оба движка работают одновременно. Посторонние туннели (в том числе `omarchy-usque`) не проверяются и не переключаются: WARP включается и выключается независимо от них. Единственная внешняя проверка — конфликт с `omarchy-zapret2.service`, который одновременно перехватывает тот же трафик; попап и `doctor` предупреждают о нём.

Пока WARP включён, системный виджет сети считает активным подключением сам туннель: `kichwarp`, адрес `198.18.0.1`, шлюз `198.18.0.2`, тип «Ethernet (10gbit)» — скорость TUN отдаёт так. Маршрут по умолчанию действительно принадлежит туннелю, поэтому это ожидаемо: адрес и шлюз реального интерфейса видны после выключения WARP. На доступ в интернет это не влияет — проверка связи проходит, предупреждения «ограниченный доступ» нет.

## Команды

`./kich-dpi` — обычный исполняемый файл, все ответы в JSON:

```bash
./kich-dpi status            # состояние для панели
./kich-dpi on | off | toggle # включить/выключить
./kich-dpi check             # проверить три сайта
./kich-dpi check-all         # только включённые сервисы + система (кнопка в попапе)
./kich-dpi generate          # сгенерировать и измерить стратегии
./kich-dpi strategies        # сохранённые варианты
./kich-dpi use <id>          # применить сохранённую
./kich-dpi doctor            # диагностика
./kich-dpi repair            # автоматическая починка известных поломок
./kich-dpi logs 100          # журнал службы
pkexec ./kich-dpi setup      # поставить/обновить движок и mihomo
pkexec ./kich-dpi remove [--purge]

./kich-dpi warp-on | warp-off | warp-toggle
./kich-dpi warp-register     # создать аккаунт, если его нет (--force — заново)
./kich-dpi warp-check        # идёт ли трафик через WARP
```

Повторные `setup`/`update`, `on`/`off`, `warp-on`/`warp-off`, `warp-config`,
`warp-register`, `repair` и `generate` не переписывают неизменённые файлы и не
перезапускают уже здоровые службы. Флаги `--force` у `warp-config`,
`warp-register` и `generate` явно обновляют результат заново.

Кэши проб (`check.json`, `warp-check.json`, `progress.json`) считаются
телеметрией: явные `check`/`repair`/`generate` обновляют в них время и
результат, поэтому критерий «байт-в-байт» применяется к управляемым файлам
(юниты, polkit, sysctl, `state.json`, `active.json`, `warp.yaml`, build-stamp,
`strategies.json`, `dpi-domains.txt`, `/etc/hosts`), а не к этим кэшам.

## Диагностика

- `journalctl -u kich-dpi -f` — журнал `nfqws2` и менеджера.
- `journalctl -u kich-dpi-warp -f` — журнал mihomo.
- `./kich-dpi doctor` — движок, mihomo, аккаунт WARP, юниты, polkit, curl, nft, конфликт с `omarchy-zapret2`. Например, намеренно выключенная служба помечается как «отключена намеренно», а не как поломка.
- Если служба падает сразу после старта, проверьте, что ядро поддерживает `nf_tables`/`NFQUEUE`, есть `/dev/net/tun` и что другой обход не держит очередь `230`.
- WARP не поднялся: `./kich-dpi warp-check` покажет `warp=on/off` и флаг `tun` (идёт ли обычный трафик через `kichwarp`), а `warp-register` пересоздаст аккаунт, если Cloudflare его отклонил. `journalctl -u kich-dpi-warp` после `ExecStartPre` начинается с ошибки `mihomo -t`, если конфиг или список правил сломан.
- Свои списки: `./kich-dpi warp-on` пересобирает конфиг и переустанавливает `rules/` из `/opt/kich-dpi/app/data/rules`. Если списков там нет (старая системная часть), команда прямо скажет обновиться.
- После смены сети подбор стоит повторить: у разных провайдеров работают разные комбинации.
- `setup` проверяет новую версию движка через GitHub API. Он без авторизации даёт только 60 запросов в час, поэтому при исчерпании лимита (HTTP 403) менеджер теперь определяет тег через `/releases/latest` без API и продолжает обновление — тревожное сообщение «сеть недоступна» при уже актуальном движке больше не появляется. Архив всё равно проверяется распаковкой.
- Пока попап открыт, он опрашивает `status` каждые 2.5 с (1.2 с во время подбора); после закрытия таймер останавливается и фоновых процессов нет. Один опрос — это один процесс Python + **один** `systemctl show` на все три юнита сразу (`kich-dpi`, WARP и конфликтующий `omarchy-zapret2`). Тесты отдельно проверяют, что `status_data()` делает ровно один `systemctl`-вызов.

## Тесты

```bash
python3 -m unittest discover -s . -p 'test_core.py' -v
```

Тесты собирают конфигурации, проверяют уникальность стратегий и, если найден `nfqws2`, прогоняют каждую через `--dry-run`. Конфиг WARP проверяется как YAML, а при наличии бинарника — через `mihomo -t`. Отдельные тесты покрывают списки правил (домены и префиксы), режим `find-process-mode` при пустом и заполненном `direct-processes.txt`, отказ на запятую в имени процесса, проверку через прокси с флагом `tun` и наличие `ExecStartPre` перед `ExecStart`:

```bash
KICH_DPI_ENGINE_DIR=/opt/kich-dpi/engine/current \
KICH_DPI_MIHOMO=/opt/kich-dpi/mihomo \
python3 -m unittest discover -s . -p 'test_core.py' -v
```
